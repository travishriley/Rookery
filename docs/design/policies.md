# Privacy, Backup, Recovery, and Approval Policy

Status: proposed default policy `0.1.0`; no real records, destinations, identities, keys, or approval exist in Phase 0.

## Privacy and Data Lifecycle

Keep software Git separate from private printer records. Public examples are generated synthetic data with fictional IDs and placeholder hashes, not redactions of a real printer. Raw source bytes, secrets and original photographs stay in an access-controlled private store outside the repository. Secret-bearing originals require encryption at rest before persistence; if secure storage/key recovery is unavailable, block persistence rather than silently storing plaintext. Use OS credential storage or a reviewed key broker, never config/CLI arguments/Git. Product encryption dependencies/format need review before implementation.

Sanitized derivatives are separate objects with redaction/preprocessing provenance and new hashes. Preview filenames, text, image pixels, EXIF/location and background content; stripping metadata alone does not redact a photograph. Public Git history stores only explicitly approved sanitized reports, never a supposed complete backup. Logs record IDs/digests and redacted failure details, not credentials/full requests.

Local-only is the default and has no remote fallback. A later cloud request needs opt-in for the exact provider, data categories, purpose and retention policy, with preview. Verify provider image/frame/schema/context/privacy capabilities at request time. An OpenAI-compatible endpoint does not imply identical image semantics. Consumer subscriptions do not imply API access. Manual sanitized chat-bundle export/import uses the same untrusted schema/policy gates without login automation.

Proposed retention: preserve approved experiment manifests, receipts, failed/rejected outcomes and referenced evidence until the owner explicitly retires them; no automatic deletion of referenced objects. Unreferenced temporary data may be purged after a configurable 30-day quarantine and a dry-run reference check. Provider raw request/response retention is redaction-aware and explicitly configured; keep replayable sanitized output when permitted. Erasure is an explicit private-store operation with journal tombstones, backup-destination accounting and disclosure that previously public Git content cannot reliably be recalled.

## Backup Gate

Default: three verified full-fidelity backup copies excluding live working files, in documented independent failure domains, at least one off-device. A private immutable local snapshot can count once if it is not the working source; two separate folders/partitions on one physical disk do not count as independent copies. Sanitized GitHub history counts zero full-fidelity copies. Independent local media can satisfy offline policy while explicitly disclosing the absence of off-site protection. Example topology for review only: private workstation snapshot, disconnected external media, independently managed encrypted off-device archive. No real topology is configured.

Each destination needs an opaque identity, storage-device/account/provider/failure-domain evidence, off-device/off-site status, full-fidelity classification, encryption/key-recovery reference, retention configuration and health. Shared account/key/ransomware failure modes are recorded, not hidden by different URLs. Independence is a policy decision backed by evidence, not string uniqueness alone.

Capture the entire approved include/inheritance/project/saved-state closure with original bytes and recovery metadata. Detect changes during capture, missing dependencies, cycles, partial reads, path escapes and ambiguous settings. Store verified source digest separately from destination archive digest (encryption may change archive bytes). Receipts bind snapshot, destination object/version, content and archive hashes, read-back verification, temporary restore manifest, timestamp, verifier and failures. Upload acknowledgement alone never yields `verified`.

Before staging modified files, require three current verified qualifying receipts and successful restore verification into isolated temporary roots. Before approval/export, rehash sources and validate receipts against the configured policy/freshness window. The human sets freshness bounds explicitly for the deployment; absent bounds cannot authorize a candidate. Read-only audit may proceed with `backup_not_ready`. Provider outage, corrupt read-back, missing key, disk-full or unverifiable failure-domain claims block candidate writes with BACKUP_FAILED. Never reduce the configured copy count automatically.

Retain previous verified snapshots until replacement copies and restores pass and the owner-approved retention policy permits retirement. Avoid destructive synchronization as the sole backup. Key recovery must be tested separately from the machine storing the main key, without committing keys or secret recovery material. GitHub-backed sanitized history is an audit adapter; GitLab and encrypted Drive/remote full archives follow later.

## Offline Candidate and Recovery

Only structured file/key/value changes within the versioned allowlist can reach a writer. Verify base bytes, values, units, parameter limits and backup gate before allocating modified candidate output. Macro/hardware-critical edits cannot be materialized in the MVP. No free-form replacement, arbitrary script, output path or G-code execution interface.

Use an isolated staging root that is not a source, printer mount, cloud sync folder or queue-watched directory. Write unique temporary files; verify bytes and manifest; publish an immutable package reference only after completion. Failure preserves previous objects and quarantines incomplete data. On restart, reconcile journal and manifest references, recheck hashes/backup/approval, and require the interrupted transition again. Recovery never imports, activates, restarts or resumes anything.

Local export is an explicit human command to a user-selected offline destination checked for source/staging overlap, links and known remote/sync/queue roots. Unknown destination suitability requires manual review; software cannot enumerate every external watcher. Revalidate approval/source/policy, then export precisely approved immutable bytes and verify them. Record destination, package digest, observed source time and operation ID. No upload adapter exists.

## Human Approval Protocol

Every packet includes run identity, original/proposed raw and semantic diffs, images/regions, measured defects, competing hypotheses/counterevidence, alternatives, expected benefits/regressions, confidence limits, policy findings, complete generated artifact and ranges, source/runtime uncertainty, backup receipts, test instructions, and rollback reference. A rollback reference points to verified originals for manual recovery; it never authorizes automatic activation.

Approval scopes: `baseline_package_review`, `candidate_export`, `test_package_review`. Each record binds printer digest, base snapshot, candidate where relevant, evidence bundle, raw G-code/artifact, geometry, toolchain, effective settings, policy, prompt, diagnostic provider/model, risk scope and intended operation. Record authenticated human actor, timestamp, expiry, rationale, review evidence and revocation status. ApprovalRecord is evidence submitted to an independent validator, not authority merely because it parses.

Local solo workflow proposal: interactive CLI displays a digest-bound packet and requires explicit human confirmation through an authenticated OS session/local approval broker. The model, background automation and candidate writer have no broker credential. Do not accept approvals from diagnostic output, unattended flags/environment variables or CI. If human versus automation identity cannot be separated in a deployment, approval remains unsupported there until a reviewed authentication mechanism exists.

GitHub experiment workflow (Phase 3): configured repository stable ID, authorized human reviewers distinct from automation author, relevant submitted review state, current withdrawal/dismissal state and required successful check identities must be verified through authenticated reads. Approval references exact reviewed packet digests and intent. A PR merge, label, issue comment, version or commit SHA alone cannot authorize an experiment. Rebase/merge content mappings need digest checks; repository reviews and experiment approvals are different protocols. Repo-only software PR approval does not authorize any printer test.

Candidate/source change, evidence expiry, policy/risk change, scope mismatch, withdrawn approval, changed reviewer policy or unmet required check invalidates authorization. Validate immediately before export and record the evaluated facts. Physical activation and every print remain manual, separately observed and attributed. Where loaded/runtime evidence is inaccessible, mark confidence/scope explicitly and block comparison if policy requires it; never synthesize firmware validation from slicer-only data.

## GitHub and CI Policy

Repository is public, which GitHub documents as eligible for protected branches on Free plans; the owner's paid plan was not inspected. Observed rulesets are empty and `main` is unprotected. No protection is enforced by this document. Recommend PR-only changes, human approval, stale-review dismissal, approval of the latest push, required successful named checks, resolved conversations, and no force-push/deletion; include administrators where supported and review bypass identities. [GitHub protection documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

A solo owner cannot supply an independent approving review on a PR authored as that same account. Review the collaborator/account workflow before enabling a required approval count that could deadlock the repository. Do not silently weaken a rule to merge. Phase 0 PR remains open, without automation self-review or merge.

B01 will implement named fixture checks before making them required: `design-contracts`, `unit-fixtures`, `boundary-fixtures`, and `restore-fixtures` as they become real. Phase 0 installs no workflow and claims no passing CI. Future CI uses hosted/isolated fixture runners, minimal `contents: read`, no printer-network routes/live mounts/decryption keys/credentials, immutable reviewed Action SHAs, no untrusted `pull_request_target` execution, and no privileged cache/artifact promotion from untrusted jobs. See [Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use).
